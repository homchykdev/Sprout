# Чек-лист: как заставить ИИ-агента делать работу хорошо без повторений

## Что показывают исследования (почему файл короткий)
- Файл инструкций, сгенерированный самим ИИ (`/init`), в тестах на 138 реальных репозиториях снижал успех задач и поднимал стоимость примерно на 20%. Он в основном дублирует то, что агент и так найдёт в репозитории.
- Файл, написанный человеком и содержащий только неочевидное, давал в среднем около +4% к успеху, но тоже увеличивал стоимость.
- Обзор структуры проекта в файле не ускорял поиск нужных файлов. Агенты читают дерево сами.
- Агенты выполняют инструкции буквально, даже когда это вредит (в одном исследовании названный в файле инструмент вызывался в 160 раз чаще). Поэтому правила пишите как условия, а не как «всегда делай X везде».
- Ориентир по размеру: до 150 строк (у Anthropic для аналогичного файла до 200). Длиннее — агент начинает пропускать правила.
- Из 2303 изученных файлов безопасность, производительность и UI/UX описывали редко (меньше 15%). Именно UI/UX и проверку результата нужно добавлять осознанно.

## Что ОГРАНИЧИТЬ (не писать в AGENTS.md)
- Описание проекта, обзор папок, содержимое README
- Стандартные правила языка («пиши чистый код», PEP8, Prettier): это делают линтеры
- Команды, которые уже есть в `package.json`
- Пожелания на будущее («хорошо бы…»): только правила, которые нужны на каждом действии
- Всё, что агент может понять из кода

## Что ДОБАВИТЬ
- Зафиксированный стек и запрет менять его без вопроса
- Определение «готово» с обязательной проверкой в браузере (скриншоты, консоль, состояния)
- Правила, в которых агент ошибается повторно (добавляйте по факту, см. ниже)
- Границы: что нельзя и о чём спрашивать
- Короткие правила дизайна и анимации; подробности вынесены в скилл `ui-quality`, чтобы загружались только по необходимости
- Бриф проекта (`docs/BRIEF.md`): заполняется один раз, чтобы не повторять одно и то же в каждом чате

## Часть 1. Одноразовая настройка (на ПК)
- [ ] Положить `global/AGENTS.md` в `~/.config/opencode/AGENTS.md` (на Windows обычно `C:\Users\<имя>\.config\opencode\`; если путь другой — проверьте в документации opencode)
- [ ] Выбрать сильную модель для сборки. Слабая модель не вытянется никакими инструкциями
- [ ] Установить Node.js и pnpm; установить Chrome (нужен для браузерных инструментов)
- [ ] Создать **шаблон-стартер** (Vite + React + TS + Tailwind + shadcn + motion), закоммитить; все новые проекты начинать копированием шаблона
- [ ] Положить в шаблон: `AGENTS.md`, `opencode.json`, `docs/BRIEF.md`, папку `.opencode/` из этого набора
- [ ] Проверить конфиг: `opencode run "test"`. Я не мог проверить его на вашей версии opencode, поэтому при ошибках схемы сверьтесь с актуальной документацией
- [ ] Убедиться, что браузерный MCP реально работает: попросить агента открыть localhost и сделать скриншот
- [ ] Отключить глобально лишние MCP; подключать только нужные проекту (каждый MCP добавляет описания инструментов в контекст)

## Часть 2. На каждый новый проект (5 минут)
- [ ] Скопировать шаблон-стартер
- [ ] Выполнить `/brief`: агент задаст вопросы одним сообщением и заполнит `docs/BRIEF.md`
- [ ] Добавить 1–3 референса (ссылки или скриншоты приложений, которые нравятся)
- [ ] Выбрать уровень анимации (сдержанно / богато) и тему (светлая / тёмная / обе)
- [ ] Закоммитить бриф

## Часть 3. На каждую задачу
- [ ] Формулировать результат и критерий готовности, а не способ («пользователь может X и видит Y»)
- [ ] Большую фичу начинать в режиме Plan: агент пишет `docs/plan.md`, вы правите, затем одобряете
- [ ] Одна задача = одна цель. Несколько мелких задач лучше одной огромной
- [ ] После сборки смотреть не только на «готово», а на отчёт: что проверено, что нет
- [ ] Выполнить `/verify`, если агент не показал скриншоты и результаты проверок
- [ ] Для визуального качества: `/polish` отдельным проходом, когда логика уже работает
- [ ] Если результат неудачный, а задача важная: прогнать её 2–3 раза в отдельных git worktree и выбрать лучший вариант
- [ ] Делать коммит после каждой рабочей версии, чтобы можно было откатить

## Часть 4. Сопровождение (самое важное)
- [ ] Начинайте с короткого файла. Не расширяйте «на всякий случай»
- [ ] Агент ошибся → одной строкой добавьте правило в `AGENTS.md` **только если ошибка повторилась** второй раз
- [ ] Раз в месяц просматривайте файл: удаляйте устаревшее, дубли и то, что агент и так делает правильно
- [ ] Следите за размером: больше ~150 строк → вынести в скилл или `instructions`
- [ ] Не просите ИИ сгенерировать весь `AGENTS.md` за вас; пусть предлагает правки, а решаете вы

## Честные ограничения
- Инструкции повышают шанс на хороший результат, но не гарантируют «идеальное приложение с первого раза». Это моя оценка, а не измеренный факт.
- Самое сильное влияние даёт связка: фиксированный стек + проверка в браузере + хороший бриф + сильная модель.
- Конфиги и названия MCP-пакетов могли измениться; перед использованием проверьте их по документации.
