# Plan: in-app logging (Журнал работы приложения)

## Цель
Пользователь может узнать, что происходило в приложении и какие были ошибки,
без Android logcat и чужих инструментов: логи накапливаются на устройстве
и экспортируются одним файлом из Настроек.

## Дизайн

### 1. Ядро — `src/lib/logger.ts` (новый, единственная точка логирования)
- Ring buffer в памяти, cap **300** записей, старые вытесняются.
- Запись: `{ ts, level: "debug"|"info"|"warn"|"error", tag, message, data? }`.
- API: `logInfo(tag, msg, data?)`, `logWarn`, `logError`, `logDebug`, `getLogs()`, `clearLogs()`, `formatLogs()` (текстовый вид для экспорта).
- Хранение: свой ключ `pulse.logs` в localStorage (НЕ zustand-store из `store.ts`,
  чтобы не раздувать пользовательские данные и не трогать миграции).
  Сброс debounce ~1.5 с + на `visibilitychange`/`pagehide`; запись в try/catch (квота).
- `debug`-записи сохраняются только если включён режим «Подробные логи» (настройка в prefs).
- Защита и гигиена:
  - клиентский код only (guard `typeof window !== "undefined"` — проект на TanStack Start со SSR);
  - никакой рекурсии: логгер сам ничего не пишет через console внутри обогащённого вывода;
  - усечение: message ≤ 2000 символов, data сериализуется safeStringify;
  - redact: шаблоны `sk-…`, `AIza…`, `Bearer …` маскируются; **никогда не логируем
    содержимое сообщений пользователя, промпты и API-ключи** — только факты
    (статус, длительность, модель, имена маршрутов).
- Подключение источников (однократно, idempotent, при первом импорте модуля):
  - обёртка `console.warn` / `console.error` (клиент);
  - `window.onerror` и `unhandledrejection`;
  - старт сессии: одна info-запись с версией сборки + платформа.
  - Корневой ErrorComponent и `reportLovableError` уже зовут `console.error` →
    покрываются обёрткой автоматически, менять `__root.tsx` почти не нужно.

### 2. Инструментирование ключевых потоков (точечно, только в catch/важных событиях)
- запросы к ИИ (`src/lib/chat/client.ts`, `ai.functions.ts` клиенты): старт/финал,
  модель, длительность, HTTP-статус, ошибка — без текста запроса/ответа;
- резервные копии (`DataGroup.tsx`, `chat/backup.ts`): успех/ошибка импорта-экспорта;
- молчаливые catch в `voice.ts` / `media.ts` / `notify.ts` / `native-reminders.ts`:
  добавить `logError`/`logWarn` там, где ошибка сейчас проглатывается;
- события расписания/последнего дня пропускаются — не логируем.

### 3. UI в Настройках — `components/game/settings/LogsGroup.tsx` (новый)
Секция «Диагностика» после `DataGroup`:
- строка-сводка: сколько записей, когда последняя;
- **Экспортировать логи** — скачивание `pulse-logs-ГГГГ-ММ-ДД.txt`
  (тот же blob-паттерн, что в `DataGroup.doExport`);
- **Скопировать** в буфер / **Поделиться** через `navigator.share` (Android);
- **Очистить логи** — с Dialog-подтверждением (как «Сбросить всё»);
- превью последних ~20 записей (раскрытие/сворачивание, уровень цветом);
- переключатель «Подробные логи (debug)» → сохраняется в prefs в `store.ts`.
- Регистрация в `routes/settings.tsx` (`<LogsGroup />`).

### 4. Тесты `src/lib/__tests__/logger.test.ts`
- вытеснение при переполнении cap;
- redact ключей/токенов;
- уровни: debug отбрасывается при выключенном режиме;
- формат экспорта (стабильный текст).

6. DoD: `pnpm typecheck && pnpm lint && pnpm test && pnpm build`; dev-сервер +
   Playwright: пройти main flow, проверить появление записей, экспорт/очистку,
   скриншоты 390/1440, консоль чистая.

## Риски
- **Квота localStorage** — mitigated cap'ом буста и try/catch; логи не критичные данные.
- **Двойное логирование** (наш хук × h3/server) — клиентский guard, на сервер не пишем.
- **Приватность** — redact + политика «только факты»; в экспорт не попадает
  содержимое чатов и ключи (проверить тестом).
- **React StrictMode / двойные эффекты** — хуки ставятся один раз на модуль.
- Затрагивает ~6–8 файлов → по workflow ждём OK до старта.

## Out of scope
Серверные log-файлы, удалённая отправка (Sentry и т.п.), поиск/фильтр по логам в UI.
